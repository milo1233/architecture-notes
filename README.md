## 1. 기능이 무한히 붙는 에이전트 베이스

**사내 메신저에서 자연어로 업무 시스템을 다루는 에이전트 서버** · TypeScript, LangGraph.js, MCP, PostgreSQL(Prisma·pgvector), Langfuse

### 문제

"티켓 만들어줘", "이 문서 요약해줘" 같은 요청을 처리하는 에이전트를 만들 때,
가장 쉬운 길은 요청 종류마다 분기를 추가하는 것입니다.

그런데 이 방식은 **기능이 늘수록 코어가 같이 부풀어 오릅니다.**
새 기능 하나에 라우팅·상태·프롬프트를 조금씩 건드리게 되고, 반년 뒤엔 아무도 코어를 못 만집니다.

사내 도구는 요청이 계속 늘어납니다. 처음부터 그걸 전제로 설계해야 했습니다.

### 판단

Anthropic의 「Building Effective Agents」 등을 읽고 내린 결론은,
**확장을 코어 수정이 아니라 인터페이스 구현으로 흡수해야 한다**는 것이었습니다.

그래서 바깥과 닿는 지점을 네 개로 끊었습니다.

| 경계 | 바뀌는 것 | 코어가 알면 안 되는 것 |
|---|---|---|
| **채널** | 메신저가 바뀌어도 | 어떤 메신저인지 |
| **도구** | 업무 시스템이 늘어나도 | 어떤 API인지 |
| **LLM** | 모델을 갈아끼워도 | 어떤 벤더인지 |
| **저장소** | 저장 방식이 바뀌어도 | 어디에 저장하는지 |

새 기능은 도구 인터페이스 구현 하나로 끝나야 하고, 그래프는 안 건드려야 합니다.

### 구조

```
START → router ─ /명령 ──→ run_command ──────────────────→ END
          │
          └ @멘션 → understand ⇄ clarify   (HITL: interrupt / resume)
                        │
                        ↓ 정보 충분
                    planner → agent ⇄ [ auth_gate → tools ]   ← ReAct 루프
                                 │
                                 ↓ 완료
                             respond → END
```

두 가지가 이 그림의 핵심입니다.

**`clarify` — 모호하면 실행하지 않고 되묻습니다.**
에이전트가 가장 위험한 순간은 잘못 이해한 채로 실행하는 때입니다.
`understand`에서 정보가 부족하다고 판단하면 그래프를 멈추고(interrupt) 사람에게 묻고,
답이 오면 그 지점부터 다시 진행합니다(resume).

**`auth_gate` — 권한 검사를 루프 안쪽에 둡니다.**
도구 실행 직전마다 호출자의 계정 권한을 확인합니다.
입구에서 한 번만 검사하면 ReAct 루프가 도는 도중에 권한 밖 데이터에 닿을 수 있습니다.
에이전트는 사람이 볼 수 있는 것까지만 봅니다.

### 결과

초기 구현 후 **7주 동안 신규 피쳐 49건**이 이 베이스 위에 올라갔습니다.
그동안 **코어 그래프 변경은 583커밋 중 20건(3.4%)** 이었습니다.

설계 의도가 실제로 지켜졌는지 사후에 측정한 숫자입니다.

## 2. 조용히 멈춘 큐 — 3중 원인 분해

**조직 업무 가시화·AI 요약 플랫폼** · Node.js(Express), PostgreSQL, React

### 문제

LLM 요약을 생성하는 큐가 어느 시점부터 일부 항목을 처리하지 않았습니다.
에러도 안 나고, 죽지도 않고, 그냥 **특정 건들이 영원히 안 돌았습니다.**

재시도 로직도 있고 차단기도 있는데 왜 복구가 안 되는지가 핵심 질문이었습니다.

### 판단

로그만 봐서는 안 잡혔습니다. 추측으로 고치면 또 재발할 것 같아서
**운영 DB를 직접 떠서 실제 상태를 세어봤습니다.**

원인이 하나가 아니라 셋이었고, 서로를 가리고 있었습니다.

| # | 원인 | 왜 안 보였나 |
|---|---|---|
| 1 | 재시도 상한이 작동하지 않음 | 상한을 넘겨도 기록만 되고 흐름은 그대로 |
| 2 | 에러를 **문자열로** 분류 | 메시지 문구가 바뀌면 분류가 통째로 빗나감 |
| 3 | 차단기의 skip을 실패로 오분류 | 잠깐 건너뛴 것이 영구 실패로 기록됨 |

세 번째가 결정적이었습니다. **일시적인 상황이 영구 배제로 굳고 있었습니다.**
LLM 사용량 한도나 외부 서비스 일시 장애는 시간이 지나면 풀리는데,
그때 이미 큐에서 빠져 있으니 다시 돌 기회가 없었습니다.

### 조치

- 에러를 **문자열이 아니라 구조로** 분류했습니다. `transient` 플래그를 두어
  "지금은 실패했지만 나중엔 될 수 있는 것"과 "영원히 안 되는 것"을 나눴습니다
- 서킷브레이커를 제대로 걸어, 차단 상태와 실패 상태를 구분했습니다
- 재시도 상한이 실제로 흐름을 끊도록 고쳤습니다

### 결과

**영구 배제돼 있던 311건이 자동으로 복구**됐습니다.
이후로는 한도 초과나 외부 장애로 실패해도 상황이 풀리면 스스로 다시 돕니다.

### 이어서 — 고치기 전에 재는 습관

이 장애 직전에 LLM 사용량 한도를 초과한 적이 있었습니다.
그때 프롬프트를 먼저 줄이지 않고 **관측부터 붙였습니다.**
호출별 토큰·비용 테이블과 관리자 대시보드를 만든 다음, 그 데이터로 낭비를 찾았습니다.

- 요약 캐시 무효 판단이 지나치게 민감했던 부분을 교정
- 프롬프트 공통 접두부를 5자 → 762자로 정렬해 콜당 캐시 재사용 +8.5k 토큰

세 건 다 **대시보드를 보고 나서야 보인 것**입니다. 감으로 줄였으면 못 찾았을 겁니다.

## 3. 서로 엉킨 Manager 들을 Mediator 로 끊기

**제조 현장의 레거시 패널 화면을 웹으로 옮기기 위한 사내 개발 프레임워크** · React(TypeScript), Playwright, Vitest · 9명 팀

### 문제

프레임워크 안에 기능별 Manager 가 여럿 있었고, **서로를 직접 참조**하고 있었습니다.
A 가 B 를 부르고 B 가 다시 A 를 부르는 형태가 쌓이면서 순환참조가 생겼습니다.

```
   ManagerA ⇄ ManagerB
      ↕    ✕     ↕
   ManagerC ⇄ ManagerD
```

당장 동작은 했지만 두 가지가 막혔습니다.

- **하나를 고치면 어디까지 영향이 가는지 알 수 없었습니다.** 참조가 양방향이라 호출 경로를 끝까지 따라가야 했습니다
- **떼어낼 수가 없었습니다.** 모바일 버전을 만들 때 Manager 하나만 가져오려 해도 나머지가 전부 딸려왔습니다

두 번째가 실제 계기였습니다. 파생 프로젝트에서 재사용하려면 구조를 먼저 풀어야 했습니다.

### 판단

Manager 들이 **서로를 알고 있는 것 자체**가 원인이라고 봤습니다.
호출 경로를 정리하는 걸로는 부족하고, 서로를 모르게 만들어야 했습니다.

그래서 두 가지를 같이 적용했습니다.

**Mediator** — Manager 끼리 직접 부르지 않고, 가운데 중재자를 통해서만 소통합니다.
각 Manager 는 다른 Manager 의 존재를 모릅니다. 관계가 N×N 에서 N 으로 줄어듭니다.

**port 인터페이스만 노출** — Manager 는 자기 구현을 감추고 필요한 창구만 밖으로 냅니다.
Mediator 는 그 창구를 통해서만 주입하고 조율합니다.

```
   ManagerA ─port─┐
   ManagerB ─port─┼──→  Mediator  (조율·주입)
   ManagerC ─port─┤
   ManagerD ─port─┘

   각 Manager 는 서로를 모른다. Mediator 만 전체를 안다.
```

### 패턴 이름

`port` 로 한정해서 노출하는 방식은 **Ports and Adapters**, 다른 이름으로
**Hexagonal Architecture** 입니다 (Alistair Cockburn, 2005).
코어가 port 라는 인터페이스만 내놓고, 바깥 세계는 adapter 로 꽂히는 구조입니다.

다만 **이걸 두고 "헥사고날 아키텍처를 적용했다"고 말하면 과장**입니다.
실제로 한 일은 이쪽에 가깝습니다.

| 적용한 것 | 무엇 |
|---|---|
| **Mediator** (GoF) | 동료 객체가 서로 직접 참조하지 않고 중재자를 통해 소통 |
| **Ports** 의 어휘 | 구현을 감추고 인터페이스만 노출 |
| **인터페이스 분리 원칙**(ISP) | 쓰지 않는 것에 의존하지 않게 창구를 좁힘 |
| **최소 지식 원칙**(Law of Demeter) | 서로에 대해 아는 범위를 줄임 |

헥사고날의 핵심인 **도메인과 인프라의 의존 방향 역전**까지 간 건 아닙니다.
프레임워크 내부 모듈 간 결합을 푸는 데 Ports and Adapters 의 어휘를 빌려 쓴 쪽입니다.

### 까다로웠던 지점 — 초기화 순서

Mediator 를 넣고 나서 부팅이 깨졌습니다.

각 Manager 가 자기 `init` 안에서 다른 Manager 를 쓰고 있었는데,
Mediator 주입이 그 `init` 보다 늦게 일어나면 **아직 아무것도 연결되지 않은 상태**가 됩니다.
직접 참조일 때는 import 시점에 이미 존재했으니 드러나지 않던 문제였습니다.

초기화를 세 단계로 쪼개서 풀었습니다.

```
1. 전체 생성        모든 Manager 를 만들되, 서로를 쓰지 않는다
2. Mediator 주입     이 시점에 관계가 연결된다
3. init             이제 다른 Manager 를 써도 안전하다
```

**"만드는 것"과 "연결하는 것"과 "쓰기 시작하는 것"을 분리**한 셈입니다.
의존성 주입에서 흔히 쓰는 순서인데, 여기서는 순환참조를 풀면서 자연스럽게 필요해졌습니다.

### 결과

결합이 풀리자 **Manager 클래스를 공통 패키지로 떼어낼 수 있었습니다.**
지금은 **PC 버전과 모바일 버전 2개 프로젝트가 같은 베이스를 참조**합니다.
한쪽에서 고친 것이 다른 쪽에 그대로 반영되고, 공통 로직을 두 번 쓰지 않습니다.

애초에 목표가 "구조를 예쁘게"가 아니라 **"떼어내서 재사용"** 이었고, 그게 실제로 됐습니다.

### 같은 프로젝트에서 한 다른 일

- **Playwright 기반 E2E 환경 구축** — CI 헤드리스 모드 지원, `workers=1` 로 DB 격리.
  테스트끼리 같은 DB 를 건드려 간헐적으로 깨지던 문제를 병렬도를 포기하고 안정성으로 바꿨습니다
- **그리드 라이브러리 마이그레이션** — `peerDependencies` 로 선언해
  라이선스 인스턴스가 싱글톤으로 유지되게 했습니다. 중복 설치되면 라이선스 검증이 깨집니다
- **admin endpoint 분리** — axios 인스턴스는 하나로 유지하면서 `baseURL` 만 다중 관리하는 방식으로 전환

## 4. 실시간 중계 플랫폼 1인 개발

**인터넷 중계방송 서비스** · React, Spring Boot, MySQL, WebRTC, SRS, STOMP · 3개월 · **1인**

### 문제

TV처럼 **채널**이 있고 그 아래 프로그램이 종속되는 구조의 중계 서비스였습니다.
송출자 화면과 시청자 화면을 모두 만들어야 했고, 혼자였습니다.

어려웠던 지점은 방송 기능 자체보다 **송출자가 화면을 "구성"하게 만드는 부분**이었습니다.
카메라 하나를 그대로 내보내는 게 아니라, 여러 소스를 합쳐 하나의 방송 화면을 만들어야 했습니다.

### 구성해야 했던 것

```
[카메라]  ─ 크로마키로 배경 제거 ─┐
[화면 캡처] ─ 표시 영역 편집 ────┤
[자막/텍스트] ──────────────────┼→  하나의 통합 스트림  →  WebRTC  →  SRS
[배경 이미지] ───────────────────┤
[마이크] + [화면 오디오] ─ 트랙 병합 ─┘
```

- 카메라 배경 제거(크로마키)
- 디스플레이·특정 프로그램 화면 캡처와 표시 영역 편집
- **화면에서 나오는 오디오를 마이크 트랙과 병합** — 이게 까다로웠습니다
- 자막 업로드, 텍스트 편집(폰트·색·정렬), 배경 이미지
- 구성해둔 화면 배치를 여러 개 저장하고 방송 중에 전환

### 송출·수신 구조

방을 `agent`라는 단위로 두고, 그 고유값으로 송출과 수신을 연결했습니다.

- 송출자는 통합 스트림을 `agent` 고유값으로 SRS에 올림
- 시청자는 같은 `agent`에 참여해 그 값으로 스트림을 받음
- 방 생성과 참여자 구성은 Spring 메시지 컨트롤러가, 실시간 메시지는 STOMP가 담당
- 채팅도 같은 `agent` 위에 얹음

방 식별자 하나로 송출·수신·채팅이 모두 묶이니, 참여 처리가 단순해졌습니다.

### 결과

3개월 동안 혼자서 송출자 화면 구성기, 스트림 송출, 시청자 수신, 채팅까지 만들었습니다.

지금 보면 화면 구성기를 더 작은 단위로 쪼갰어야 했습니다.
소스 종류가 하나 늘 때마다 편집 로직을 같이 고쳐야 했습니다.

## 5. 1,960줄 컴포넌트를 무중단으로 해체하기

**조직 업무 가시화 플랫폼의 프론트엔드** · React(TypeScript), react-router, TanStack Query

### 문제

최상위 컴포넌트 한 파일이 **1,960줄**이었습니다.
렌더·상태·데이터 fetch·타입 정의가 전부 거기 있었습니다.

돌아가고는 있었지만, **어디를 건드려도 무엇이 깨질지 알 수 없는 상태**였습니다.
서비스는 이미 사내에서 쓰이고 있어서 멈출 수 없었습니다.

### 판단

한 번에 뜯으면 반드시 뭔가 깨집니다. 그리고 깨진 걸 모릅니다 — 비교할 기준이 없으니까요.

그래서 **분해보다 먼저 현행 동작을 테스트로 고정**했습니다.
지금 코드가 "옳은지"는 묻지 않고, "지금 이렇게 동작한다"만 박아둡니다.
그 뒤에 리팩터링해서 테스트가 그대로 통과하면, 동작이 안 바뀐 겁니다.

> **특성화 테스트(Characterization Test)** — Michael Feathers, *Working Effectively with Legacy Code*.
> 레거시를 "명세가 없는 코드"로 정의하고, 손대기 전에 현재 동작을 캡처해 안전망을 만드는 기법입니다.

그리고 **세 단계로 쪼개서** 한 번에 한 종류의 변화만 일으켰습니다.

### 1단계 — 순수 이동만

먼저 **동작을 전혀 바꾸지 않는 것만** 했습니다.

- 중복 유틸(응답 파싱·에러 메시지·날짜 포맷)을 공용 모듈로 추출
- 인증 화면·설정 모달·대시보드 뷰를 프레젠테이션 컴포넌트로 이동

옮길 때 규칙을 하나 뒀습니다 — **JSX 는 그것만 먹이는 state 와 함께 옮기고,
여러 곳이 쓰는 상태는 그대로 두고 props 로 내린다.**
욕심내서 상태까지 재설계하면 1단계가 아니라 전면 개편이 됩니다.

### 2단계 — 탭을 URL 로

`useState` 로 관리하던 화면 전환을 라우터 URL 로 올렸습니다.
새로고침과 딥링크가 되고, 화면 전환 상태가 최상위 컴포넌트에서 빠집니다.

인증 게이트는 **라우터 바깥의 전체 게이트로 유지**했습니다.
라우트마다 인증을 거는 구조로 바꾸면 그건 이동이 아니라 설계 변경입니다.

### 3단계 — 데이터 계층

매 마운트마다 직접 부르던 fetch 를 선언적 쿼리로 옮겼습니다.
여기서 가장 중요한 판단은 **라이브러리의 똑똑한 기본값을 일부러 껐다**는 것입니다.

```
retry: false                    재시도 안 함
refetchOnWindowFocus: false     창 포커스에 다시 안 부름
staleTime: 0                    캐시 신선도 판정 안 함
```

이 기본값들은 보통 켜는 게 좋습니다. 그런데 켜는 순간 **요청 타이밍이 달라집니다.**
리팩터링에서 동작이 달라지면 그건 리팩터링이 아니라 기능 변경입니다.
먼저 동작을 그대로 옮기고, 개선은 별도로 하는 게 맞다고 봤습니다.

폴링도 마찬가지로 **기존 주기를 테스트로 고정**하고 옮겼습니다
(요약 폴링 4000ms × 20회, 다른 하나 1500ms).

### 결과

**1,960줄 → 167줄 (−91%).** 배포 후 회귀 **0건.**

숫자보다 중요한 건 이제 **한 곳을 고칠 때 영향 범위를 말할 수 있다**는 점입니다.

## 6. 디자인 명세를 RAG 로 태워 UI 를 생성하기

**내부망 디자인 협업툴의 AI 고도화 PoC** · LangGraph, RAG, 디자인툴 플러그인, Node.js

### 문제

디자인 시스템 명세·개발 가이던스·레이아웃 규칙이 문서와 디자인 파일에 흩어져 있었습니다.
"이 규칙들을 데이터로 만들어서, 사용자 요청을 받아 규칙에 맞는 화면을 생성할 수 있는가"를
검증하는 과제였습니다.

핵심 난점은 **디자인 정보가 한 가지 형태가 아니라는 것**이었습니다.
컴포넌트는 생김새(이미지)이자 구조(트리)이자 용도(자연어)입니다. 어느 하나만으로는 부족합니다.

### 판단 — 멀티모달 청킹

한 컴포넌트를 **세 조각으로 나눠 담고, 메타데이터로 다시 이었습니다.**

| 조각 | 무엇 | 답할 수 있는 질문 |
|---|---|---|
| **Visual** | 캡처 이미지 | "이렇게 생긴 게 뭐지" |
| **Structural** | 디자인툴 트리 XML | "이건 어떻게 조립돼 있지" |
| **Semantic** | 자연어 설명 | "언제 쓰는 거지" |

셋을 따로 넣으면 검색 결과가 파편화됩니다. 그래서 **메타데이터를 연결고리로 두어**
한 조각이 걸리면 나머지를 같이 끌어오게 했습니다.

DB 도 **컴포넌트용과 UX 문서용으로 분리**했습니다. 성격이 다른 문서가 한 인덱스에 있으면
서로의 검색 품질을 갉아먹습니다. 대신 프롬프트에 **소스 우선순위 규칙**을 주입해
어느 쪽을 먼저 믿을지 정했습니다.

### 파이프라인

한 번에 화면을 만들라고 하지 않고, 결정을 단계로 쪼갰습니다.

```
요구사항 확장 → 섹션 레이아웃 결정 → 슬롯 후보 결정
   → 컴포넌트 확정 → 내부 레이아웃·variant 결정 → 렌더링
```

각 단계가 앞 단계의 결과만 받으므로, 어디서 틀렸는지 짚을 수 있습니다.

- **슬롯 후보 선정** — 슬롯 힌트와 컴포넌트 스냅샷으로 RAG 매칭, 유사도 0.6 이상만 통과
- **카탈로그 자동 생성** — 컴포넌트 메타데이터를 LLM 으로 만들고 스냅샷으로 관리.
  손으로 쓰면 컴포넌트가 늘 때마다 사람이 따라가야 합니다
- **렌더링 스펙 재설계** — 전체 트리를 통째로 넘기던 방식에서 변경분만 넘기는 배열 방식으로 전환.
  환경변수 분기로 기존 방식과 나란히 돌려 호환을 유지했습니다
- **유효성 필터** — 파싱에 실패하면 거기서 예외를 내고 멈춥니다.
  깨진 스펙이 렌더링까지 흘러가면 어디서 틀렸는지 못 찾습니다

인수인계 없이 넘겨받은 코드라, **코드를 역추적해 프롬프트·state·스키마를 복원**하고
슬롯 선정 노드 기준으로 파이프라인 정합성을 먼저 맞췄습니다.

### 검증 — 규칙을 바꿔서 결과가 따라오는지 본다

"결과물이 그럴듯한가"는 판정 기준이 못 됩니다. LLM 은 항상 그럴듯합니다.

그래서 **대조 실험**을 했습니다.

1. 제시된 컴포넌트와 레이아웃 규칙이 결과물에 반영되는지 확인
2. **기반 규칙을 의도적으로 바꾼 뒤** 다시 생성 → 바뀐 규칙이 결과에 나타나는지 확인

2번이 핵심입니다. 이게 되어야 모델이 **규칙을 실제로 읽고 따르는 것**이지,
그럴듯한 UI 를 외워서 뱉는 게 아니라는 근거가 됩니다.

## 7. 조직 암묵지를 LLM 이 참조하게 만들기

**조직 업무 가시화 플랫폼의 리스크 예측** · LLM CLI, 파일 기반 지식 위키, Docker

### 문제

조직 운영에는 문서화되지 않은 판단 기준이 있습니다.
"정책이 안 정해졌는데 개발이 병행되면 위험하다" 같은 것들입니다.

실제 사례를 분석해 **리스크 패턴 10종(P1~P10)과 관리 게이트**로 정리하고,
LLM 이 요약을 만들 때 참고하도록 파일 위키로 넣었습니다.

그런데 배포하고 보니 **AI 요약 18개 문장에 `[근거:]` 인용이 0건**이었습니다.
출처 표기는 있는데, 위키를 근거로 든 문장이 하나도 없었습니다.
내용상으로는 P2·P6·P7 에 해당하는 이야기를 하고 있는데도요.

### 진단 — 전면 고장이 아니라 편차였다

먼저 **어느 구간에서 사라지는지**부터 봤습니다.
파서 → sanitize → 프론트 렌더링을 전 구간 추적한 결과, 근거 태그는 전부 보존되고 있었습니다.
출력 경로의 문제가 아니었습니다.

그다음 **같은 시점에 재생성된 다른 프로젝트들을 비교**했습니다.

```
프로젝트 A   근거 6건
프로젝트 B   근거 15건
프로젝트 C   근거 0건     ← 문제가 보고된 곳
```

**전면 회귀였다면 전부 0건이어야 합니다.** 편차가 있다는 건 조건부로 실패한다는 뜻입니다.

원인은 여기 있었습니다. 위키 인덱스에 `리스크 패턴 10종(P1~P10)` 이라고만 적혀 있고
**각 패턴의 인용 키와 이름은 상세 파일 안에** 있었습니다.
즉 모델이 그 파일을 열어봐야만 인용 키를 알 수 있는데, **파일을 열지 말지는 모델 재량**입니다.
열면 인용하고, 안 열면 0건. 그래서 프로젝트마다 갈렸습니다.

### 조치

**인용 키를 항상 보이는 자리로 옮겼습니다.**
인덱스에 패턴 카탈로그 표를 인라인하되, **인용 키와 감지 신호 요약만** 실었습니다.
원문 전체를 프롬프트에 싣는 것과는 다릅니다 — 위키 컨텍스트는 1,131자 → **2,208자**로만 늘었습니다.

파일을 안 열어도 대조와 인용이 가능해지고, 상세가 필요할 때만 열게 됩니다.
**토큰 비용은 고정한 채 인용 가능성만 올린 것**입니다.

회귀 방지 테스트도 걸었습니다 — 위키 컨텍스트에 P1~P10 인용 키가 **항상** 노출되는지 검사합니다.

### 결과

같은 프로젝트에서 근거 태그 **0건 → 10건**. 특정 패턴을 정확히 짚어 인용하는 것까지 확인했습니다.

### 곁가지 세 개

**(1) 컨테이너에서는 파일이 안 열렸다**

로컬에서는 되는데 운영 컨테이너에서만 실패했습니다.
원인은 LLM CLI 가 내부적으로 쓰는 샌드박스였습니다 — 컨테이너에서 권한 없는 user namespace 가
막혀 있어 샌드박스가 뜨지 못했고, 그래서 파일 읽기 명령이 실패하고 있었습니다.
**로컬에서 같은 버전으로 성공하는 걸 먼저 실증**해 "도구가 못 읽는다"와 "환경이 막는다"를 갈랐습니다.

조치는 실패를 감지하면 내부 샌드박스를 우회하고 이후 유지하는 런타임 폴백입니다.

**(2) 우회하면서 비밀을 같이 끊었다**

샌드박스를 우회한다는 건 보호막을 하나 걷어낸다는 뜻입니다.
그래서 **자식 프로세스에 넘기는 환경변수를 최소로 줄였습니다** —
DB 비밀번호, 시크릿, 암호화 키를 전부 제거했습니다.
프롬프트 인젝션으로 환경변수를 읽어내려 해도 **거기에 아무것도 없게** 만드는 쪽입니다.

**(3) 위키를 고쳤더니 전량 재생성이 돌 뻔했다**

요약 재생성 여부를 판정하는 **지문(fingerprint)** 에 위키 서명이 섞여 있었습니다.
인덱스 한 줄을 고쳤더니 지문이 통째로 바뀌었고, 그대로 배포했으면
**프로젝트 51개와 마일스톤 39개가 전량 재생성**될 상황이었습니다.

문구를 고칠 때마다 수천 건의 LLM 호출이 나가면 **아무도 프롬프트를 개선하지 않게 됩니다.**
개선 비용이 높으면 개선이 멈춥니다.

- 지문에는 **원본 티켓 데이터만** 넣도록 바꿨습니다. 새 프롬프트는 티켓이 바뀔 때 자연히 적용됩니다
- 옛 계산식을 재현하는 함수를 따로 두고, 저장값이 그것과 일치하면
  **LLM 호출 0회로 지문만 새 값으로 갱신**했습니다. 이관 비용이 0입니다
- 이 규칙을 테스트로 못박고 테스트 스위트 **맨 앞에서** 돌립니다.
  재생성을 유발하는 스위치 상수들도 핀으로 잠갔습니다
- 과잉 고정을 막기 위해 **티켓이 실제로 바뀌면 지문이 바뀌는지도** 같이 검사합니다

## 8. 개선을 증명하려면 대조군을 먼저 얼려야 한다

**모바일 화면을 UX 휴리스틱 34종으로 자동 평가하는 도구** · TypeScript, Electron, Vitest

### 문제

평가 파이프라인이 **한 벌뿐**이었습니다.
프롬프트를 고치든 호출 구조를 바꾸든, **고치는 순간 비교 대상이 사라집니다.**

"좋아진 것 같다"는 말은 할 수 있지만 증명할 수는 없는 상태였습니다.
그리고 LLM 파이프라인은 같은 입력에도 결과가 흔들리기 때문에, 인상만으로 판단하면 거의 틀립니다.

### 판단

**개선 직전 상태를 통째로 복제해 얼리고, 개선은 사본에만** 했습니다.

- 파이프라인 11모듈과 관리형 자산 28종(프롬프트 18 + 휴리스틱 3 + 응답 스키마 7)을 플로우마다 한 벌씩
- 실행 진입점 세 가지 — 대조군 단독 / 개선안 단독 / **둘을 사람 개입 없이 연달아 돌리는 비교 모드**
- 결과는 이슈 1건 = 1행으로 내보내고, 어느 플로우에서 나왔는지를 열로 갈라 바로 비교

한 가지 구조를 먼저 바꿔야 했습니다. **에이전트 반복 횟수를 화면이 쥐고 있었습니다.**
그대로 두면 두 플로우가 그 코드를 공유하게 되어, 한쪽을 고치면 다른 쪽이 따라 변합니다.
호출 계층으로 내려 각 플로우가 자기 것을 갖게 했습니다.

### 얼린 것이 실제로 얼어 있게 하기

선언만으로는 안 지켜집니다. **기계가 막게** 했습니다.

- 대조군 폴더 **46개 파일의 SHA-256** 을 대조하는 테스트. 테스트 스위트와 커밋 훅 양쪽에서 실행
- 원본 `.md` 와 거기서 생성된 코드를 **둘 다** 해싱 — 생성물만 보면 자산이 몰래 바뀝니다
- **탈출구를 일부러 남겼습니다.** 완전히 잠그면 불가피한 수정 때 훅 우회가 습관이 됩니다.
  승인 명령을 두어 "우회했다"는 사실이 기록에 남게 하는 쪽을 골랐습니다

잠금장치도 갈아끼웠습니다. 처음엔 `A = B` 를 증명하는 테스트를 뒀는데,
설계대로 **개선 첫 커밋에서 실패**했습니다. 그래서
`A 는 원본 결함을 유지하고 B 는 고쳐졌다` 를 의미 수준에서 잠그는 테스트로 바꿨습니다.

### 그리고 — 비교가 성립하지 않았다

개선 후 돌려 보니 **양쪽 다 이슈가 거의 안 나왔습니다.**
"대조군 경로가 오염된 것 아니냐"는 의심이 나왔고, 네 가지로 확인했습니다.

| 확인 | 결과 |
|---|---|
| 개선 전후 diff | README 만 변경 |
| 46개 파일 해시 대조 | 통과 |
| 대조군이 폴더 밖에서 쓰는 것 | 셋 다 무변경 |
| 커밋 내 코드 변경 | 화면 표시·내보내기·개선안 전용. 실행 경로 무변경 |

**가장 결정적인 근거는 대조군 자신의 데이터였습니다.**

```
             이슈(A/B)      A1 추출(A/B)     A3 추출(A/B)
기준선         2 / 3          90 / 88         126 / 119
이후 3회    0·1·0 / 4·0·0   90·88·75 / …    82·102·83 / …
```

**대조군 코드는 네 번 내내 바이트 단위로 동일한데 결과가 흔들립니다.**
오염이 있었다면 한 방향으로 치우쳐야 하는데 그렇지 않았습니다.
대조군이 스스로 대조군 역할을 해 준 셈입니다.

그래서 내린 결론은 "개선됐다"가 아니라 이것이었습니다.

> **대조군 변동폭(0~2)과 개선안 변동폭(0~4)이 완전히 겹친다.
> 파이프라인 노이즈가 둘의 차이보다 크므로, 몇 회 표본으로는 판단할 근거가 없다.**

"그전엔 2건씩 고정으로 나왔다"는 인상은 표본 1건이었습니다.
변동폭은 추출 기준이 주관적일수록 컸습니다 — ±10% / ±21% / ±28%.

**개선을 주장할 수 없다고 보고하는 것**이 이 단계의 결과물이었습니다.

## 9. 프롬프트가 스스로를 부정하고 있었다

### 판정을 원천 봉쇄하던 두 문장

세 에이전트의 판정 프롬프트에 똑같이 들어 있던 조건입니다.

> 위반은 **추론 없이, 다른 휴리스틱과의 비교 없이, 맥락 가정 없이** 명백할 때만 인정한다.

둘 다 성립하지 않는 지시였습니다.

- **"다른 휴리스틱과 비교 없이"** — 판정 단계는 한 호출에 휴리스틱을 **하나만** 받습니다.
  비교 대상이 존재하지 않으므로, 모델이 이 문장으로 할 수 있는 일은 "애매하면 빼라" 뿐입니다
- **"맥락 가정 없이"** — 이 파이프라인은 맥락을 만들려고 **앞 단계를 통째로 돌립니다.**
  그렇게 만든 맥락을 판정 단계가 "맥락이 필요하면 명백한 게 아니다"로 무효화하고 있었습니다

둘을 걷어내고 화면과 맥락을 **쓰라고** 명시했습니다.

### 억제 지시가 46회

같은 취지의 문장이 시스템 프롬프트에 4번, 사용자 프롬프트 **맨 끝**에 1번 반복되고 있었습니다.
마지막 자리는 가중치가 큰데 그 자리가 "내지 마라"였습니다.

```
억제성 표현    대조군 46회  →  개선안 12회
```

동어반복과 "빈 배열을 내는 것이 valid 하고 expected 하다"는 권장 문장을 지웠습니다.
**날조 금지는 남겼습니다** — 대신 애매한 건은 근거를 적어 보고하게 했습니다.
근거를 못 대면 스스로 걸러집니다.

### "없음"을 근거로 쓰게 하기

한 에이전트는 **16회 실행 전부 0건**이었습니다. 노이즈가 아니라 구조적인 문제였습니다.

세 프롬프트를 나란히 놓으니 그 에이전트에만 있는 문장이 보였습니다 —
**"보이지 않는 흐름이나 숨은 동작을 추측하지 말 것."**

그런데 이 에이전트만 **「없는 것」을 판정**합니다. 경고가 없다, 취소 수단이 없다, 복구 경로가 없다.
없다고 말하려면 화면에 안 보이는 것을 근거로 삼아야 하는데 그게 금지돼 있었습니다.

**부재의 증거는 이미 기록돼 있었습니다.** 로딩 화면 13장의 복구 항목이 전부 빈 배열,
25장 전부 닫기 없음. 기록은 됐는데 **그것을 근거로 세라는 말이 없었습니다.**

빈 배열과 false 플래그가 "찾아봤고 없었다"는 **관측**이며 추측이 아님을 명시했습니다.
추측 금지 자체는 남겼습니다 — 화면 밖 동작을 지어내는 것과는 다릅니다.

결과: 순차·병렬 두 실행에서 같은 건이 재현됐고, 같은 실행 안의 대조군은 둘 다 0이었습니다.
표본 2회라는 한계도 함께 적었습니다.

### 검출을 열었더니 중복이 따라왔다

억제를 풀자 한 요소가 여러 휴리스틱에 걸려 **같은 곳이 2~2.6배로 세어졌습니다.**
한 문구가 6개 휴리스틱에 걸린 실행도 있었습니다.

검출 단계에서는 막을 수 없습니다 — 각 지적은 자기 휴리스틱 관점에서 **다 맞고**,
한 호출에 휴리스틱이 하나뿐이라 "중복 피하라"는 지시가 성립하지 않습니다.

그래서 **검출은 그대로 두고 보여줄 때 묶었습니다.** 후처리라 호출이 늘지 않고 비용이 0입니다.
버리는 이슈가 없다는 것(대표 + 나머지 = 원본 건수)을 테스트로 잠갔고,
**일부러 안 묶는 것**도 정했습니다 — 에이전트가 다르면 보는 것이 다르고,
요소를 특정 못 하는 건(「취소 수단이 없다」 같은 부재)은 묶으면 정보가 사라집니다.

## 10. 입력 토큰의 87%가 이미지였다

### 문제

한 번 실행에 호출이 38회 나가고, **매 호출이 같은 화면 25장을 통째로 다시 싣고** 있었습니다.

```
입력 30,902 토큰 = 텍스트 3,952 + 이미지 26,950
실행 1회 이미지만 약 1,024,100 토큰
```

모델의 암묵 캐싱은 **요청 앞에서부터 일치하는 만큼만** 재사용합니다.
그런데 코드는 정반대였습니다 — `[텍스트, 이미지…]` 순이라
**매 호출 바뀌는 프롬프트가 맨 앞**에 있었고, 첫 글자에서 일치가 끊겨 뒤의 이미지는 영영 캐시되지 않았습니다.

### 고친 것

단계마다 **이미지 먼저, 텍스트 나중**으로 싣게 했습니다.
프롬프트 본문은 **한 글자도 건드리지 않았습니다** — 본문 안의 순서도 역순이지만,
추가 이득이 2~3천 토큰인데 내용이 바뀌면 품질 변수가 늘어납니다.

```
정가로 계산되는 입력    31,223  →  2,934   (91% 감소)
```

캐시 적중이 이미지 토큰보다 많았는데, 차이는 시스템 지시문과 프롬프트 앞머리였습니다.

**결과가 안 바뀌었음을 확인**했습니다. 순서 변경 전 3회 / 후 3회를 돌려
이슈 건수 평균 14.3 / 14.3, 특정 화면의 특정 문구는 여섯 번 전부 정확히 4건이었습니다.

### 요금 계산이 틀려 있었다

모델이 돌려주는 입력 토큰 수는 **캐시 적중분을 포함한 총합**인데,
그걸 통째로 정가 입력으로 보내 **90% 할인받은 토큰을 정가로 계산**하고 있었습니다.
캐시분을 분리했습니다.

가격표 자체에도 오류가 있었습니다 — 출력 단가 자리에 입력 단가가 들어가 있어
출력 비용이 **1/5** 로 잡히고 있었습니다.

> 앞서 "캐싱이 일어나지 않으니 이 작업은 불필요"라고 판단했던 것은 **틀렸습니다.**
> 로그를 보니 대조군의 한 단계는 이미 23,634 토큰이 적중하고 있었습니다 —
> 그쪽은 원본 결함 때문에 프롬프트가 매 실행 동일해서, 요청 전체가 바이트 동일했던 것입니다.
> "구조상 불가능"은 일부 단계에만 맞는 말이었습니다.

### 파고들다 발견한 것 — 이미지 토큰은 격자다

위치 좌표를 붙일 수 있는지 시험하다가, **해상도를 바꿔도 이미지 토큰이 변하지 않는다**는 걸 봤습니다.
92×200 썸네일과 1080×2340 원본이 같은 토큰을 씁니다.

장당 토큰은 **모델이 그림 한 장에 매기는 고정 요금**이지 사진의 성질이 아니었습니다.
숫자를 분해하니 격자가 보였습니다.

```
하위 모델   258 = 16×16 + 2    셀 하나 68×146px
상위 모델  1078 = 22×49        셀 하나 49×48px
```

**텍스트 한 줄이 약 40px** 이므로 하위 모델의 셀 하나는 **세 줄을 덮습니다.**
그 모델의 좌표 중심 적중률이 23% 였던 건 성의 문제가 아니라 **눈금 문제**였습니다.
오차도 편향이 아니라 산포라서 보정 상수로 고칠 수 없었습니다.

여기서 나온 실무 결론들:

- **사진을 줄여도 비용이 줄지 않는다** — 절반 해상도도 같은 토큰. 원본을 그대로 보내는 게 맞다
- **처리 속도도 해상도와 무관** — 지연을 정하는 것은 출력·사고 토큰
- **모델 간 토큰 수 비교는 함정** — 하위 모델이 싸 보이는 건 화면을 덜 보기 때문이고, 그 대가가 적중률이다
- **비용을 조절할 수 있는 지점은 모델 선택과 호출 횟수뿐** — 그래서 캐싱이 사실상 유일한 큰 수단이었다

## 11. 우리 개선안은 아직 사람 한 명에 못 미친다

### 고객사의 물음

> "선행과제의 검출 결과는 102개입니다. 이러면 개선 후 결과가 더 나아졌다고 할 수 있는지 모르겠습니다."

우리 산출은 그보다 훨씬 적었습니다. 답하기 전에 **그 102가 무엇인지**부터 확인했습니다.

### 전수 대조

제공받은 원자료 세 시트를 전부 파싱해 우리 실행 기록과 맞췄습니다. 입력 화면은 25장으로 동일했습니다.

**102건은 AI 산출물이 아니라 사람 다섯 명의 합계였습니다.**
평가자 5명이 AI 를 보조로 쓰면서 각각 한 시간씩 평가한 **사람 대상 실험**이었고,
AI 없이 진행한 대조군은 40건이었습니다.

근거는 자료 안에 다 있었습니다 — 평가자별 건수(11·28·10·37·16), 소요 시간과 노동량,
평가자 간 신뢰도 분석 시트.

```
단위를 맞추면      1인 환산 20.4건   대   우리 1회 51건
```

고객사도 102를 성과 숫자로 쓰고 있지 않았습니다. 시트에 클러스터 열이 있어
102건은 64 클러스터로 접히고, 성과 지표는 전문가가 인정한 건수와 시간당 노동량이었습니다.

그리고 **짚은 곳은 87% 같았습니다** — 우리가 지적한 문구 15개 중 13개가 고객사 대상 안에 있었습니다.

### 여기서 멈추지 않은 이유

개수 정정만으로 답하면 **다음 질문에서 무너집니다** — "그래서 놓친 건 없나요?"

그래서 선행과제 대상 21개를 기준선으로 삼아 저장된 실행 기록 14건의
**커버리지와 정밀도를 측정**했습니다. 무작위로 찍었을 때의 기대 적중도 함께 계산해서,
높은 적중률이 남발의 부산물인지 아닌지 가를 수 있게 했습니다.

| 산출 | 적중률 | 커버리지 |
|---|---|---|
| 대조군 | 100% | 5 ~ 14% |
| **개선안** | 67~100% | **9 ~ 29%** |
| 하위 모델(남발형) | 83~93% | 48 ~ 62% |
| **사람 1인** | — | **평균 35%** |

### 결론 — 우리 개선안은 아직 부족하다

**개선안의 커버리지는 사람 한 명분에 못 미칩니다.**
"개선됐다"는 주장은 중복 제거 축에서는 방어되지만 **커버리지 축에서는 아직 방어되지 않습니다.**

그리고 남발형 모델의 48~62% 가 **이 화면 세트에서 문턱을 낮추면 도달 가능한 선**을 알려주므로,
다음 목표치가 숫자로 생겼습니다.

결론은 "낮은 문턱으로 돌아가자"가 아니라
**"문턱을 낮추면서 병합과 근거 품질을 유지하자"** 였습니다.

### 자기 초안에서 뺀 것

모델 적합성을 평가하면서 초안에 넣었다가 **근거가 부족해 철회한 지적이 둘** 있었습니다.
상위 모델도 방어 수단이 없는 항목이라, 모델 탓으로 돌리면 불공정한 평가가 됩니다.

- 한 항목은 우리 쪽 파서가 필드를 읽지 않고 버리는 문제였습니다. 어떤 모델로 돌려도 같은 결과입니다
- 다른 하나는 "부재를 지적하는 것이 본업인 에이전트"의 정당한 지적이었고,
  우리 자료 구조에 담을 자리가 없어 어느 쪽이 옳은지 **가릴 재료가 없었습니다**

측정하는 쪽이 유리한 결론을 낼 수 있는 위치에 있을 때, **뺄 것을 빼는 것**도 측정의 일부라고 봤습니다.
