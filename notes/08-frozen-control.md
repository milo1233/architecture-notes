# 개선을 증명하려면 대조군을 먼저 얼려야 한다

**모바일 화면을 UX 휴리스틱 34종으로 자동 평가하는 도구** · TypeScript, Electron, Vitest

### 문제

평가 파이프라인이 **한 벌뿐**이었습니다.
프롬프트를 고치든 호출 구조를 바꾸든, **고치는 순간 비교 대상이 사라집니다.**

"좋아진 것 같다"는 말은 할 수 있지만 증명할 수는 없는 상태였습니다.
그리고 LLM 파이프라인은 같은 입력에도 결과가 흔들리기 때문에, 인상만으로 판단하면 거의 틀립니다.

### 판단

**개선 직전 상태를 통째로 복제해 얼리고, 개선은 사본에만** 했습니다.

- 파이프라인 11모듈과 관리형 자산 28종(프롬프트 18 + 휴리스틱 3 + 응답 스키마 7)을 플로우마다 한 벌씩
- 실행 진입점 세 가지 — 대조군 단독 / 개선안 단독 / **둘을 사람 개입 없이 연달아 돌리는 비교 모드**
- 결과는 이슈 1건 = 1행으로 내보내고, 어느 플로우에서 나왔는지를 열로 갈라 바로 비교

한 가지 구조를 먼저 바꿔야 했습니다. **에이전트 반복 횟수를 화면이 쥐고 있었습니다.**
그대로 두면 두 플로우가 그 코드를 공유하게 되어, 한쪽을 고치면 다른 쪽이 따라 변합니다.
호출 계층으로 내려 각 플로우가 자기 것을 갖게 했습니다.

### 얼린 것이 실제로 얼어 있게 하기

선언만으로는 안 지켜집니다. **기계가 막게** 했습니다.

- 대조군 폴더 **46개 파일의 SHA-256** 을 대조하는 테스트. 테스트 스위트와 커밋 훅 양쪽에서 실행
- 원본 `.md` 와 거기서 생성된 코드를 **둘 다** 해싱 — 생성물만 보면 자산이 몰래 바뀝니다
- **탈출구를 일부러 남겼습니다.** 완전히 잠그면 불가피한 수정 때 훅 우회가 습관이 됩니다.
  승인 명령을 두어 "우회했다"는 사실이 기록에 남게 하는 쪽을 골랐습니다

잠금장치도 갈아끼웠습니다. 처음엔 `A = B` 를 증명하는 테스트를 뒀는데,
설계대로 **개선 첫 커밋에서 실패**했습니다. 그래서
`A 는 원본 결함을 유지하고 B 는 고쳐졌다` 를 의미 수준에서 잠그는 테스트로 바꿨습니다.

### 1차 수정 직후 — 판정을 미뤘다

1차 수정 후 돌려 보니 **양쪽 다 이슈가 거의 안 나왔습니다.**
"대조군 경로가 오염된 것 아니냐"는 의심이 나왔고, 네 가지로 확인했습니다.

| 확인 | 결과 |
|---|---|
| 개선 전후 diff | README 만 변경 |
| 46개 파일 해시 대조 | 통과 |
| 대조군이 폴더 밖에서 쓰는 것 | 셋 다 무변경 |
| 커밋 내 코드 변경 | 화면 표시·내보내기·개선안 전용. 실행 경로 무변경 |

**가장 결정적인 근거는 대조군 자신의 데이터였습니다.**

```
             이슈(A/B)      A1 추출(A/B)     A3 추출(A/B)
기준선         2 / 3          90 / 88         126 / 119
이후 3회    0·1·0 / 4·0·0   90·88·75 / …    82·102·83 / …
```

**대조군 코드는 네 번 내내 바이트 단위로 동일한데 결과가 흔들립니다.**
오염이 있었다면 한 방향으로 치우쳐야 하는데 그렇지 않았습니다. 대조군이 스스로 대조군 역할을 해 준 셈입니다.

이 시점의 판단은 "개선됐다"도 "안 됐다"도 아니었습니다.
**대조군 변동폭(0~2)과 개선안 변동폭(0~4)이 겹치니, 이 숫자로는 아직 가를 수 없다** — 그래서 판정을 미루고
왜 **둘 다** 조용한지를 먼저 팠습니다.

### 원인 — 「애매하면 보고하지 마라」가 46번

지시문 곳곳에 같은 취지의 억제 문장이 46번, 마지막 문장까지 "보고하지 마라"였습니다.
한 번에 기준을 하나만 받는 모델에게 "다른 기준과 비교 없이", 맥락을 만들려고 앞 단계를 통째로 돌리면서
"맥락 가정 없이" 같은 **지킬 수 없는 조건**도 걸려 있었습니다. → [9. 프롬프트가 스스로를 부정하고 있었다](09-prompt-contradiction.md)

46번을 12번으로 줄이고, 마지막 문장을 "찾은 것을 알려 달라"로 바꾸고, 애매한 건은 "빼라" 대신 "근거를 적어 보고하라"로 바꿨습니다.

### 2차 수정 후 — 같은 실행 안에서 0 대 8

| 언제 | A (대조군) | B (개선안) |
|---|---|---|
| 고치기 전 — A와 B가 같았을 때 | 2군데 | 2군데 |
| 1차 수정 후 (4회) | 0 · 1 · 0 · 2건 | 4 · 0 · 0 · 0건 |
| **2차 수정 후 (2회)** | **0 · 0군데** | **8 · 8군데** |

두 플로우는 **같은 모델 설정**을 읽고, 비교 모드는 **같은 사진을 같은 실행 안에서** 둘 다 돌립니다.
그 안에서 A 가 두 번 다 0, B 가 두 번 다 8이었습니다. "그날 운이 좋았다"로는 설명되지 않고, 차이는 지시문에서만 나옵니다.
7회 내내 0건이던 화면 일관성 담당도 이때 처음 지적을 냈습니다.

### 결론은 세 층으로 나눠 적었다

좋아진 것만 적으면 다음 판단을 그르칩니다. 그래서 결과를 셋으로 갈랐습니다.

**좋아진 것 — 2군데 → 8군데**
처음엔 "3건 → 15건"이라고 적었습니다. 그런데 한 문구가 여러 기준에 걸리면 건수가 부풀려집니다
(6회 실측 1.6~2.6배, 대조군은 정확히 1.0배). **몇 군데를 짚었나**로 다시 세니 2 → 8이었고,
"5배"가 아니라 **"2~3배 좋아졌다"**로 고쳐 적었습니다. 개선은 진짜지만 배율이 달랐습니다.

**아직 모르는 것**
- 오류 방지 담당은 1건 × 2회 — 같은 것을 두 번 다 찾았지만 표본이 작습니다
- 채점 기준 설명 복원과 지시문 수정 중 **무엇이** 결과를 열었는지는 갈라 보지 않았습니다.
  조합마다 여러 번, 최소 12회가 필요했습니다

**확실히 아닌 것**
- 요소 추출 단계에 넣은 **자기점검 지시는 효과가 없었습니다** — 추출 개수는 여전히 실행마다 20% 안팎으로 흔들렸습니다
- 지금 사진 세트엔 **오류가 뜬 화면이 한 장도 없어**, 오류 방지 기준 중 둘은 어떤 지시문으로도 나오지 않습니다.
  고칠 대상이 지시문이 아니라 사진 세트라는 뜻입니다

**개선을 주장하는 것만큼, 주장할 수 없는 것을 구분해 적는 것**이 이 단계의 결과물이었습니다.
