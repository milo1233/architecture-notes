# 조용히 멈춘 큐 — 원인 셋, 그리고 틀렸던 복구 보고

**조직 업무 가시화·AI 요약 플랫폼** · Node.js(Express), PostgreSQL, React

### 문제

LLM 요약을 생성하는 큐가 어느 시점부터 일부 항목을 처리하지 않았습니다.
에러로 죽지도 않고, 그냥 **특정 건들이 영원히 안 돌았습니다.**

재시도 로직도 있고 차단기도 있는데 왜 복구가 안 되는지가 핵심 질문이었습니다.

### 판단 — 로그 대신 운영 DB 를 셌다

추측으로 고치면 또 재발할 것 같아서 **운영 DB 를 직접 떠서 실제 상태를 세어 봤습니다.**

```
약 1시간 50분 동안 멤버 요약 호출 490건 — 전량 실패, 성공 0
10분마다 정확히 40건씩, 같은 대상을 반복
선두 40건이 처리 예산을 전부 차지 → 뒤에 밀린 1,754건은 순서가 오지 않음
```

원인이 하나가 아니라 셋이었고, 서로를 가리고 있었습니다.

| # | 원인 | 왜 안 보였나 |
|---|---|---|
| 1 | 재시도 횟수를 조회 쿼리에서 빠뜨려 **상한 검사가 항상 통과** | 코드엔 상한이 있는데 값이 비어 있어 같은 40건이 무한히 돌았다 |
| 2 | 차단기의 에러 문구가 한국어라 **영문 「일시적 실패」 패턴에 안 걸림** | 잠깐 건너뛴 것이 영구 실패로 쌓였다 |
| 3 | LLM 도구의 **로그인 만료(401) 문구**가 어느 패턴에도 없음 | 만료가 풀려도 이미 영구 배제된 뒤였다 |

2와 3은 같은 뿌리입니다 — **에러를 문자열로 분류하고 있었습니다.**
문구가 조금만 달라도 「지금은 실패했지만 나중엔 될 것」이 「영원히 안 되는 것」으로 굳었습니다.

### 조치

- 재시도 횟수를 조회에 넣어 상한이 실제로 흐름을 끊게 했습니다
- 서킷브레이커 — 일시적 실패가 5번 연속이면 30분 쉬었다가 사람 개입 없이 다시 시도합니다.
  큐를 비우는 주기 자체도 차단기로 막아, 건너뛰기 기록만 569행 쌓이던 낭비를 없앴습니다
- 에러를 문자열이 아니라 **구조로** 분류해 일시적 실패 표식을 달았습니다

### 그리고 — 복구 보고가 틀렸다

처음엔 "갇혀 있던 행은 이제 자동으로 복구된다"고 보고했습니다. **틀렸습니다.**
다시 세 보니 멤버 159건 · 팀 44건이 여전히 배제된 채였습니다.

일시적 실패 표식은 코드가 **던지는 에러 객체**에만 붙어 있었고,
DB 에 이미 저장된 실패 사유는 여전히 문자열이라 새 분류가 읽지 못했습니다. 고친 것은 앞으로의 실패뿐이었습니다.

그래서 세 가지를 더 했습니다.

- DB 에 저장하는 실패 사유에도 「일시적」 표식을 남긴다
- 그룹 요약에도 같은 판정을 적용한다
- 이미 갇힌 행은 저장된 입력 지문과 현재 지문을 비교해 되살린다 — **LLM 을 한 번도 부르지 않고**

직전 보고를 정정한 것까지가 이 장애의 결과물이었습니다.
「고쳤다」를 확인하는 기준은 코드가 아니라 **운영 DB 의 숫자**라는 걸 이때 몸으로 배웠습니다.

### 이어서 — 고치기 전에 재는 습관

이 장애 직전에 LLM 사용량 한도를 초과한 적이 있었습니다.
그때 프롬프트를 먼저 줄이지 않고 **관측부터 붙였습니다.** 호출별 토큰 · 비용 로그를 쌓아 8일 치를 보니:

```
599콜 중 조직 요약이 91% (멤버 57% · 그룹 34%)
```

그 데이터로 구조적인 낭비를 찾았습니다.

- 요약을 다시 만들지 판단하는 지문에 「티켓 수정 시각」이 들어 있어, 댓글 · 라벨만 바뀌어도 재생성 —
  이슈 1건을 고치면 최대 12콜이 연쇄로 나갔습니다 → 프롬프트가 실제로 쓰는 값만 해시하도록 교체
- 생성 대기 중인 화면이 4초마다 폴링할 때마다 새 생성 라운드(최대 12콜)가 시작 → 범위별 60초 쿨다운
- 가변값이 프롬프트 첫 줄에 있어 공통 접두부가 5자뿐 → 762자로 재정렬해 캐시가 걸릴 자리를 만듦

**대시보드를 보고 나서야 보인 것들**입니다. 감으로 줄였으면 못 찾았을 겁니다.

### 그 뒤 — 도구가 무엇을 바꿨고, 무엇은 바꾸지 않았나

플랫폼이 자리를 잡은 뒤에는 **"그래서 효과가 있었나"** 에 답해야 했습니다.
티켓 1.4만 건을 직접 집계했더니 업무 도구의 활동 총량이 도입 전후로 4.6배였습니다.

**이 숫자는 버렸습니다.**

월 단위로 보면 깔끔한 계단 하나지만, 주 단위로 끊으면 계단이 선 자리가 달랐습니다.

```
활동 총량 계단   3월 초    ← 이 도구의 첫 커밋보다 앞
참여 인원 계단   5월 말주  ← 파일럿 공개보다 한 달 앞
```

같은 시기에 조직이 업무 도구 운영을 정비하고 프로젝트를 늘리고 있었습니다.
**총량이 오른 건 그쪽 일이지 내 일이 아닙니다.** 여기서 욕심을 내면 뒤의 숫자까지 같이 의심받습니다.

### 무엇을 성과로 남길지 — 세 개의 필터

1. **시점이 배포에 붙는가** — 월이 아니라 주 해상도로 본다
2. **쓰지 않은 집단과 갈리는가** — 도구를 연 사람의 부서 전원을 한 묶음, 나머지를 대조로
3. **강제가 아닌가** — 입력이 필수로 바뀐 거라면 그건 행동 변화가 아니다

셋을 통과한 것만 남겼습니다.

| 남긴 것 | 변화 | 통과한 근거 |
|---|---|---|
| 산출물 기록률 | 2% → 89% | 수집 기능 배포 **2주 뒤** 계단 |
| 몰아서 닫기 | 61% → 30% | 완료 전이 총량은 유지된 채 비율만 이동 |
| 1인 주당 활동 | +4% (쓰지 않은 부서 −22%) | 같은 기간, 두 집단이 반대로 움직임 |

세 번째 필터는 특히 조심했습니다. 기록률이 오른 게 **필드가 필수로 바뀐 결과**라면 아무 의미가 없습니다.
확인해 보니 같은 프로젝트 안에 채운 티켓과 안 채운 티켓이 섞여 있었습니다(한 곳은 159건 중 141건).
입력을 막는 강제가 있었다면 나올 수 없는 모양입니다.

### 같이 들고 다니는 반대 증거

- 도구를 열지 않은 부서에서도 산출물 기록은 3% → 75%로 올랐습니다.
  전사 가이드라인 같은 **공통 요인이 섞여 있고**, 내 도구가 유일한 원인이라고는 말할 수 없습니다
- 도구를 본 부서는 **도입 전에도 이미 2.4배 활동적**이었습니다. 자기 선택 효과를 배제할 수 없습니다
- 기한 입력률은 오히려 73% → 32%로 **떨어졌습니다.** 기록 습관이 전방위로 좋아진 건 아닙니다
- 무작위 배정이 아니라 사후 분류입니다. 표본 81명 · 3개월, 통계 검정은 하지 않았습니다

### 재면서 배운 것

- **해상도를 잘못 잡으면 남의 성과를 내 것으로 읽습니다.** 월 단위로만 봤다면 "참여 인원 +42%" 를
  내 성과라고 적었을 겁니다. 주 단위로 끊고 나서야 계단이 파일럿보다 앞이라는 게 보였습니다
- **코호트 단위를 잘못 잡으면 결론이 뒤집힙니다.** 도구를 직접 연 사람만 묶으면 활동 증가폭이
  오히려 작습니다. 대부분 리더라 본인이 티켓을 쓰지 않기 때문입니다. 이 도구는 **리더가 보고 팀이 움직이는** 물건이라
  개인이 아니라 부서가 단위였습니다
- **상태 문자열이 쪼개져 있으면 수치가 통째로 바뀝니다.** 완료 상태가 세 가지 표기로 갈려 있었고,
  하나만 세고 결론을 낼 뻔했습니다
- **100% 는 대개 표본이 작다는 신호입니다.** 어느 주의 기록률이 100%로 보여 "필수 필드가 됐나" 를 의심했는데,
  그 주 표본이 작았을 뿐이었습니다

만든 사람이 자기 도구를 재면 숫자는 늘 좋게 나옵니다.
그래서 이 작업의 결과물은 올라간 숫자가 아니라, **올라간 것 중 내 것이 아닌 걸 골라낸 기준** 쪽이었습니다.
